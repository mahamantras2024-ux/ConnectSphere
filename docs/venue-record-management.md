# Venue record management

Venue Staff can open a venue in a panel that slides in from the right, edit its catalogue fields, or deactivate it. Deactivation is the removal action: it hides the venue from all active catalogues, including Event Coordinator searches, without deleting past booking records.

## Booking safeguards

- Updates check upcoming confirmed bookings (`approved` in the existing booking model). Ongoing bookings are protected too: a booking remains upcoming/active until its end time.
- Reduced capacity is checked against expected attendance; removed layouts are checked against the event's requested layout. Removed facilities/accessibility features and changes to location, operating hours, buffers or unavailable status prompt a precautionary review because the current booking records do not describe every facility dependency.
- The warning identifies booking number, event, date/time and reasons. Saving an affected change requires a second explicit confirmation. The server binds that acknowledgement to the exact changes, venue revision, current bookings and staff member; it expires after ten minutes. Changed booking data requires another review.
- Another staff member's edit produces a stale-record error instead of silently overwriting their changes.
- Deactivation is blocked by upcoming confirmed **and pending** bookings. Cancelled/rejected bookings and completed historical bookings do not block it.
- Database row locks and a booking trigger prevent a concurrent booking from being created for a venue while it is being deactivated. Historical booking foreign keys remain intact.

## Maps and nearest MRT

No Google account, API key or Docker service is required. Leaflet displays OpenStreetMap tiles within the venue form and detail panel. Staff type an address and press Search, then select a result, or click the map. The selected address is displayed separately from the search text.

The backend calculates the nearest MRT by straight-line distance from the selected coordinates using a checked-in snapshot of 142 MRT station locations. Browser-supplied MRT text is ignored. LRT stops and station entrances are excluded. Distance is approximate and is explicitly labelled as straight-line distance, not walking distance. The station snapshot includes Hume and Punggol Coast. Refresh the dataset when stations open or their coordinates change; it is not a live service-status feed.

Existing venues have no invented coordinates. Staff can retain their existing address when editing other details, then select a map location to enable the embedded profile map and replace legacy MRT text with the automatic calculation.

Address lookup uses the public Photon demo service with bounded results, a shared request queue, a 24-hour cache, timeouts and staff-only rate-limited endpoints. Provider failure displays an error; a clicked location still resolves to its coordinates and its nearest MRT even when reverse-address lookup is unavailable. The demo has no availability guarantee and is intended for modest traffic; configure a hosted or self-hosted provider before scaling beyond the team's prototype.

Optional configuration:

- Backend `GEOCODER_URL`: Photon-compatible base URL; default `https://photon.komoot.io`.
- Frontend `VITE_MAP_TILE_URL`: compatible tile URL; default `https://tile.openstreetmap.org/{z}/{x}/{y}.png`. Maintain visible OpenStreetMap attribution when using these tiles.

Sources: [Leaflet](https://leafletjs.com/examples/quick-start/), [Photon API and demo limits](https://github.com/komoot/photon), [OpenStreetMap tile policy](https://operations.osmfoundation.org/policies/tiles/), [SG Rail Data provenance](https://github.com/cheeaun/sgraildata).

## Database setup

From `backend`, run `npm run setup:venue-management` using the existing private database configuration. This additive, repeatable upgrade adds venue lifecycle/map/revision columns, the booking table where missing, database guards, indexes, RLS protection and notifications. Do not run the older draft full schema to upgrade an existing database.

The configured shared database has been upgraded. Teammates with separate databases must run the same setup. No existing venue was removed or deactivated during implementation.

Open catalogues subscribe to server-sent invalidation events generated by PostgreSQL after commit. Notifications refresh both cards and open detail panels. Browser focus and a twenty-second fallback poll recover when a stream cannot connect. Use a direct PostgreSQL connection or a Supabase **session** pooler for `LISTEN/NOTIFY`; transaction pooling cannot keep a listener subscribed. The configured connection uses the session pooler on port 5432. Booking/private client data are never included in public stream messages.

## API

| Operation | Endpoint | Access |
|---|---|---|
| List active venues | GET `/api/venues` | Existing public catalogue |
| View active venue | GET `/api/venues/:id` | Existing public catalogue |
| Update a venue | PUT `/api/venues/:id` | Venue Staff |
| Deactivate a venue | DELETE `/api/venues/:id` | Venue Staff |
| Search addresses | GET `/api/venues/locations/search?q=…` | Venue Staff |
| Resolve a map point + MRT | GET `/api/venues/locations/resolve?lat=…&lng=…` | Venue Staff |
| Catalogue invalidations | GET `/api/venues/stream` | No venue, booking or client payloads |

PUT accepts the complete validated venue payload, `revision`, and (when warned) the returned `confirmationToken`. HTTP 409 distinguishes `BOOKING_IMPACT`, `STALE_VENUE` and `VENUE_BOOKED` so the UI can show the appropriate next step.

## Verification

Automated HTTP/UI tests cover role enforcement, exact-change confirmation, stale changes, newly added bookings, blockers, history-preserving removal, catalogue refresh, address selection and server-calculated MRT. The opt-in PostgreSQL test uses a disposable schema and verifies persistent changes, repeated upgrades, historical joins, committed notifications and concurrent booking/deactivation serialization. Run it with the other isolated database suites from the project root using `node tests/run.cjs integration`; see [the testing guide](../tests/README.md).

The full booking request/approval workflow remains outside this change; its disconnected legacy routes were removed. The safeguards use booking records already stored in `venue_bookings` and apply to future writes through the database trigger.

Current verification and coverage instructions are in the central testing guide. Generated screenshots and earlier output reports were removed during cleanup.
