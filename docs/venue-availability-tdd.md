# Venue availability — final green Test Verification Record

Verified on **6 October 2026 (Asia/Singapore)**. All 47 failures from the approved red phase now pass. The production implementation, regression checks and isolated PostgreSQL verification are complete; human PR review and merge remain required.

**User story:** As an Event Coordinator, I want to view venue availability across relevant dates and times so that I can identify when a venue may be requested for an event.

## Implemented behavior and rationale

| AC | Behavior |
| --- | --- |
| AC1 | Coordinator dashboard exposes the venue catalogue; profiles allow date selection and schedule viewing independently of staff management permissions. |
| AC2–AC5 | Recorded confirmed bookings, maintenance and active holds determine the agenda. Text labels distinguish Available, Booked, Temporary Hold and Under Maintenance. Loading/errors hide stale availability. Refresh, focus and hold deadlines reread server records. |
| AC6 | Event occupancy is `[event start − setup, event end + turnaround)`. A 10:00–11:00 event with 30-minute setup and 15-minute turnaround occupies 09:30–11:15. Candidate and recorded event buffers are both checked; maintenance uses its recorded window. SQL includes buffer-only overlaps across midnight. |
| AC7 | A coordinator assigned to the event can submit a request. It persists as pending with a deadline exactly 24 hours after creation. Venue Staff explicitly approve or reject it. All changes apply to the slot, never the venue-wide catalogue status. |
| AC8–AC9 | A pending hold blocks only while `now < hold_expires_at`. Expiration releases that hold without a worker, preserves other blockers and never confirms a request. Historical rows remain pending for audit; effective slot availability changes. Late approval must recheck all current conflicts. |

Dates use **Asia/Singapore** and half-open intervals. Approved is the existing database status for a confirmed booking; the display also recognizes confirmed. Legacy pending rows without a deadline remain informational: the migration does not invent new holds for old records. Rejected/cancelled requests do not reserve time. Approved bookings stay booked after any historical hold deadline.

The schedule hook refetches at expiry before showing availability, so a request approved after the initial page load cannot be released by a stale pending snapshot. A failed refresh reports an error rather than claiming the slot is free. API-provided buffer values take precedence over an older catalogue snapshot.

The request service locks the venue before reading conflicts and writing. PostgreSQL guards use the same lock and interval rules for direct booking writes; maintenance changes also acquire venue locks. A late approval receives no priority from an expired hold. No cleanup job or browser is necessary for server-side expiration.

## API and deployment

- `GET /api/venues/:id/schedule?date=YYYY-MM-DD`: Venue Staff and Event Coordinators can read raw recorded periods, hold deadlines and current buffer settings.
- `POST /api/venues/:id/requests`: coordinator-only, with `eventId`, `startDatetime`, `endDatetime`; success is HTTP 201 with `{ request }`. Identity comes from authentication, not the payload. Timestamps require explicit timezones.
- `PUT /api/venues/:id/requests/:requestId/decision`: staff-only, with `decision: "approved"` or `"rejected"`; success is HTTP 200 with `{ request }`. The request lookup is venue scoped. Conflicts return 409.
- The default 24-hour policy is centralized in `HOLD_DURATION_MS` in `backend/src/services/venueAvailability.js`.
- After the existing venue-management upgrade, deploy the additive schema with `npm run setup:venue-availability --prefix backend`. It installs recorded-unavailability storage where needed, adds nullable hold deadlines and replaces/adds booking/maintenance locking guards.

**The migration was verified on real PostgreSQL 17.6 in generated disposable schemas. It was not applied to shared application tables.** The deployment database must receive the migration before the updated API serves requests. The migration runner's successful/idempotent path ran against PostgreSQL; its CLI bootstrap/error-reporting wrapper is outside the runtime coverage configuration described below.

- Generated schemas and separate connections isolate every test from application tables; teardown drops only the generated schema.
- Migration/setup repetition preserves exact existing rows, keeps legacy expiry null and does not change catalogue-wide status.
- Real schedule SQL retrieves both previous-day turnaround and next-day setup overlaps while excluding another venue.
- Both simultaneous submissions are observed waiting on actual PostgreSQL backend PIDs before a gate transaction commits. Exactly one responds 201, the other 409, and one live hold persists.
- Approval waits for an uncommitted maintenance insert, then returns 409 after that closure commits; the request remains pending.
- Direct SQL inserts test one millisecond below, exactly at and one millisecond above buffered adjacency, enforcing the same half-open rule as the API.
- Expired holds release without a worker; a replacement can reserve the slot and prevents the old request from displacing it.
